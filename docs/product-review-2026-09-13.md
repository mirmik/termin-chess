# Пересмотр Termin Chess — 13 сентября 2026

Статус: исторический снимок обзора перед реализацией. Предложение принято и
реализовано в следующем проходе; актуальные инструкции — в README и chess-mcp.md.

Реализация: выбор сторон и random, ориентация камеры, меню с паузой/продолжением,
редактор приглашения, компактный HUD, CLI и исправления MCP. Проверено 50 быстрыми
тестами, пятью сценариями настоящего player и пятью сценариями готового Linux bundle.
Дополнительно проверена раскладка на 640×480 и 360×640. Проблема графики из обзора
объяснена ограничениями песочницы: вне неё SDL/Vulkan работают. Задачи #2358–2363
реализованы; исходные наблюдения ниже оставлены как контекст изменения.

## Вывод

Игра уже имеет полезную основу: python-chess, отдельную модель владения сторонами,
компактное состояние для агента, ожидание хода, проверку прав и синхронизацию фигур.
Главный следующий шаг — закончить пользовательские сценарии вокруг этой основы.
Переписывать движок или заменять весь игровой контроллер для этого не требуется.

## Что подтверждено

| Наблюдение | Основание | Следствие |
| --- | --- | --- |
| Агент может владеть белыми, но меню этого не предлагает | `ChessGameSession.configure_human_vs_agent`, `ChessGameController._configure_requested_game_mode`, `ChessUIComponent._build_start_menu` | Нужна настройка сторон, а не новая шахматная логика |
| Случайный цвет отсутствует | В настройке используются только white/black | Разрешать random один раз при создании партии, до выдачи приглашения |
| Настройки меню читаются из окружения | `start_human_vs_agent()` не принимает конфигурацию | UI и автоматический запуск должны использовать один явный объект настроек |
| Только `CHESS_MCP=1` игнорирует `CHESS_AGENT_SIDE` | Ветка `configure_runtime()` назначает агенту black | Устранить разные правила запуска; временно задавать и `CHESS_GAME_MODE=human_vs_agent` |
| Предпросмотр и редактор приглашения отсутствуют | `agent_memo_text()` вызывается из callback копирования | Нужен доступный пользователю черновик |
| Статус clipboard виден только в логах | `ChessUIComponent._copy_text` | Показывать успех/ошибку в окне приглашения |
| HUD перегружен техническими сведениями | `_build_game_panel`, `_add_connection_section` | Вынести реквизиты в отдельное окно |
| «connected» означает первый полученный запрос | `McpSeatStatus.mark_seen` устанавливает флаг до reset | Показывать последнюю активность; нельзя заключать, что агент сейчас думает |
| «Return to Menu» уничтожает текущую позицию | `return_to_start_menu` вызывает `new_game` | Разделить продолжение партии и создание новой |
| Подписи меняются под чёрную сторону, камера кодом игры не разворачивается | `chess_ui_text.board_view/files_text/ranks_text`; камера задана сценой | Выбор стороны должен включать ориентацию и проверку picking |
| Последний ход переживает сброс | `ChessMcpRuntime.last_move_event` ищет назад без границы reset | Агент получает противоречивый снимок новой партии |
| Команда хода не привязана к партии/позиции | `make_move` принимает move и timeout | Законный в новой позиции запоздалый ход старой партии неотличим от актуального |

Для воспроизведения сброса использован настоящий контроллер с заглушками только
сценовых операций: записать событие e2e4, вызвать `new_game`, прочитать
`get_agent_state`. Результат: `ply=0`, `last_move.uci=e2e4`.
Риск запоздалой команды установлен по контракту; сетевой сценарий гонки не воспроизводился.

## Предлагаемый интерфейс

### Новая партия

Одна форма: соперник, цвет человека, краткое объяснение выбранного режима и одна
основная кнопка. Режимы: с агентом, вдвоём на одном компьютере, два агента;
встроенный бот можно открыть отдельным вариантом, он уже есть в модели.
Для игры с агентом: «Белые / Чёрные / Случайно». После случайного выбора показать
фактическое распределение. Повторная отрисовка не должна менять цвет.

После создания партии доступно приглашение соответствующему агенту. Первый ход
белых не требует хода человека: агент за белых должен сразу получить готовую позицию.
В режиме двух агентов приглашения и черновики раздельны. Ошибка запуска сервера
должна показывать причину и возможность повторить запуск.

### Партия

Основное пространство занимает доска. Рядом — игроки и их цвета, чей ход,
история SAN, последний ход и результат. На доске — координаты и подсветки.
Действия подключения, экспорт FEN/PGN, новая партия и выход не должны занимать
равное место с текущим ходом. Нужна кнопка переворота вида без смены владельцев.

Предлагаемый стиль: спокойные поверхности, хороший контраст фигур, один акцентный
цвет, устойчивые отступы и типографическая иерархия. Русские пользовательские
подписи; технические термины оставить в дополнительном разделе. Проверять
минимальное окно и масштабирование в нативном GUI, а не только макет в браузере.

Меню во время игры сохраняет партию и предлагает «Продолжить». «Новая партия»
означает отдельное действие. После окончания — понятный результат, реванш,
смена сторон и экспорт истории. Сохранение партии на диск — следующий этап,
если требуется продолжение после перезапуска приложения.

### Приглашение агенту

Окно показывает назначенный цвет и редактируемое сообщение перед копированием.
Нужны сброс к шаблону, сохранение черновика при закрытии окна и видимый результат
копирования. Реквизиты места формируются отдельно от пользовательских пожеланий;
финальный текст виден целиком. Новая партия должна обновлять реквизиты без
незаметного переноса устаревшего подключения.

В тексте приглашения перечислить конкретные команды, условия ожидания и завершения,
разрешённые способы доступа к игре и политику помощи. Текущее «не использовать
external tools» следует уточнить: утилита связи с игрой разрешена, шахматные
движки/дебютные базы — только по разрешению пользователя. Уровень сложности
не стоит обещать через «рейтинг агента», пока он ничем не измерен.

## CLI и MCP

Сейчас реализован собственный HTTP JSON-RPC сервер с MCP-методами: initialize,
tools/list, tools/call, resources/read. Документация предлагает curl; поставляемого
CLI в этом репозитории нет. Внешняя утилита, которой пользователь играет, в рамках
обзора не исследована. Работа через утилиту сама по себе не опровергает наличие MCP.

Есть конкретные расхождения с **заявленной сервером версией 2025-06-18**:

- HTTP 204 на initialized notification вместо 202.
- GET /mcp возвращает 404 вместо 405 при отсутствии SSE.
- Нет проверки MCP-Protocol-Version и Origin.
- Рекламируется resources.subscribe, но уведомления об изменениях не доставляются.

Требования проверены по [транспорту MCP 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)
и [ресурсам MCP 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/resources).
SSE не обязателен для простого ответа JSON; отсутствующую поддержку подписок можно
не объявлять. Совместимость со стандартным клиентом ещё нужно проверить отдельно.

Рекомендация: назвать пользовательский раздел **«Подключение агента»**. Основной
путь для эпизодической игры — небольшой CLI; MCP оставить дополнительным способом
использовать тот же сервис. Частота использования не является свойством протокола:
постоянство подключения определяется клиентским приложением и способом настройки.

Предлагаемая форма команд, ещё не существующий интерфейс:

```text
chess-agent connect <приглашение>
chess-agent status
chess-agent wait --timeout 60
chess-agent move e2e4
chess-agent pgn
```

CLI хранит подключение своего места, предлагает `--help` и `--json`, сообщает
понятные ошибки. `wait` возвращает актуальную позицию целиком: обычно агенту
достаточно цикла «wait → выбрать ход → move». Ответ содержит его сторону,
готовность ходить, позицию, допустимые ходы и результат партии. Список инструментов
должен содержать доступные агенту действия; new_game/set_bot_enabled сейчас
рекламируются, хотя внешним местам всегда запрещены.

Приглашение должно выдавать только своё место; общий локальный файл с обоими
токенами остаётся операторским. Для надёжности добавить game_id и ожидаемую
позицию/ревизию, проверяемые при применении хода. Это защищает от старых команд
после новой игры и смены позиции; для старых клиентов определить переход явно.

Альтернативы для обсуждения: CLI-only с честным снятием обещания MCP либо MCP
как основной путь после клиентской проверки. Создавать две независимые реализации
шахматных команд не нужно. Отдельный CLI возможен поверх текущего сервиса, а
транспортная совместимость MCP исправляется отдельно.

## Порядок работы и доска

1. Исправить границы партий; открыть выбор цвета и согласовать ориентацию.
2. Сделать редактируемое приглашение и понятный основной способ подключения.
3. Пересобрать меню и HUD по согласованному сценарию; проверить в Termin.
4. Проверить MCP обычным клиентом и устранить расхождения объявленного контракта.
